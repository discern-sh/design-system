# ADR 0054: The Markdown browser runs on the application runtime, alone or nested

**Status**: accepted; supersedes [ADR-0022](0022-browse-markdown-in-an-owned-terminal-viewport.md); amends [ADR-0024](0024-address-markdown-links-with-sgr-mouse-events.md) by moving link focus and mouse input onto the application runtime's rules, [ADR-0050](0050-applications-compose-a-grouped-list-a-following-detail-and-modal-layers.md) by adding Markdown reading bodies and nested applications, and [ADR-0053](0053-applications-paint-incrementally-and-animate.md) by ending the browser's whole, unsynchronized painting

## Context

[ADR-0022](0022-browse-markdown-in-an-owned-terminal-viewport.md) gave the Markdown browser its own owned viewport: its own input loop, its own lifecycle bracket, a picker and a document as two bordered panes sized by `allocateTerminalPanes`, Tab to switch panes, `]` and `[` for links, a query that took every printable key, and a footer of hand-written key prose. That was the right shape before the package had persistent applications. Once applications existed — a header, one body, key hints laid out by one authority, synchronized row painting, one copy table, terminal surfaces, a 32 × 10 minimum with a live notice, an opt-in mouse policy — the browser was a second, older screen beside them. It painted whole frames unsynchronized, its words lived outside the copy table, and its keys meant different things: Tab moved between panes in the browser and between groups in an application.

The difference matters most where the two meet. An application that offers its own manual could only reach the browser through a foreground handoff: release the alternate screen, print a handoff line into scrollback, run the browser as a separate request, and come back. The reader sees the screen flash to the shell and back, and learns a second key map for the manual. Asking the application to compose the browser into its own view instead does not work either: bindings are compiled once for a whole session, so the application's letter keys would still fire while the manual was on screen, and its action type would have to absorb the browser's.

## Decision

**The browser is an application.** `MarkdownBrowserController` builds `TerminalApplicationView`s from the caller's corpus and the reader's history and answers each action, followed link, and dismissal; it has no painter, key reader, or lifecycle of its own. Three screens make it up. The contents is a master-detail body: every entry under its group heading, with the selected document previewed in the following detail — its title, description, and the document as its reading shows it, with its path only when the caller asks for paths — and a strip below 80 columns. A document is a Markdown reading body. Search is a palette over every entry. `/` and Ctrl+K search, `c` shows the contents, Escape and Backspace go back through the history, and `q` closes; Escape where the browser started closes too. Every word it writes comes from `MarkdownBrowserCopy`, which extends the application copy table.

**What the browser needed, the runtime gains for every application.**

- _Markdown reading bodies._ A reading body's content may be `ApplicationMarkdown`. The package renders it at a readable measure and treats its links as controls: Tab and Shift+Tab move between them and stop at the ends, Escape leaves them first, the focused link is always on screen and scrolling leaves it, and Enter or a click follows. A link naming a heading of the same document scrolls there; any other reaches `onLink`, which returns a command as `onAction` does. Link identity comes from the neutral Markdown document and the shared cell projection, as [ADR-0024](0024-address-markdown-links-with-sgr-mouse-events.md) decided, never from re-parsing output. `context.reveal` restores a scroll position, brings a heading to the top, or focuses a link. Rewrapping keeps the line that was at the top.
- _Nested applications._ `nestTerminalApplication(options, onExit)` is a command that runs another application on the same screen, in place of the one whose action returned it, without releasing the terminal. Each application keeps its own model, keymap, callbacks, mailbox, and background work in a session; the runtime paints and feeds input to the front one. The application beneath is frozen as it was — its mailbox, reports, and timers wait, as they do during a foreground handoff — and resumes exactly where it was; `onExit` runs as one of its callbacks with the nested final state. A nested exit prints nothing, so it refuses an epilogue. An unbound Ctrl+C in a nested application closes it and reaches the one beneath as Ctrl+C, so Ctrl+C keeps one meaning across the whole session.
- _Fitted input._ Keys read together each meet the model the previous key left laid out, exactly as keys read apart do, while painting still happens once per batch. Link movement depends on where links sit on screen, so without this a pasted or fast key sequence acted on a stale layout.

**Two ways to run it, one way to answer it.** `requestMarkdownBrowser()` runs it on its own screen, refuses missing ANSI control or a terminal below the application minimum before changing anything, and resolves with the chosen action, exit, or external link and a resumable state after restoration. `markdownBrowserCommand()` returns the nested command that runs it inside a running application, and `onClose` receives where the reader was so the next opening resumes there. Both take the same `respond`: it answers an action or external link with a command while the browser stays on screen, a failed background command it returns shows its error's message, and `{ kind: "exit" }` closes the browser — alone, the request resolves with the choice it answered; nested, the opener resumes. Without `respond`, a standalone browser resolves with every choice. A caller that can act without leaving the screen, such as one opening a page, therefore never releases the terminal and starts a new browser from the resumable state, which would flash the screen and need a separate acknowledgement for a failure.

**No pane allocator.** `allocateTerminalPanes` and its viewport module are removed; the master-detail split rules size the contents and its preview.

**What it does not do.** The browser is not a reader layer: layers are bounded panels over a body, and a corpus browser needs history, search, and its own keys. It is not a body a caller composes into its own view, for the keymap reason above. Resolution stays effect-free and synchronous, so a resolver answers at once. Typing no longer searches without `/`, because printable keys are bindings in an application.

## Consequences

The browser and every application now share one chrome, one key grammar, one painter, one copy table, and one mouse policy, and an application opens its manual without leaving its screen. The Markdown reading body and nested applications are available to any caller, so a dashboard can show release notes with followable links, or open any other application in place.

The change breaks callers. The pure browser state, transition, and renderer exports and their types are gone; tests and previews drive the browser through the application model instead, and the Catalogue does so through a small preview driver. Pane minimums are gone, the resumable state has a new shape (history, contents selection, positions, focused links), resolvers are synchronous, and `]`, `[`, Tab between panes, and typing to search no longer exist. Scripts that typed into the picker press `/` first.

While a nested application is in front, the one beneath shows nothing and handles nothing: a busy dashboard does not update its rows while its manual is open, though its background work keeps running and its newest reports arrive on return. Nesting adds a stack to the runtime; its rules — frozen opener, unwinding Ctrl+C, no epilogue — are the ones the nested tests pin. The contents preview renders a whole document per selected entry; it is cached by block identity and width, so each document renders once per width.

## Alternatives considered

Keeping the browser's own loop and sharing only the painter was the interim step; it left the chrome, key map, and words separate and still forced a foreground handoff to reach the browser from an application. A browser layer would have bent the layer model — bounded, receding panels that the caller declares — around a screen that needs history and search. A body the caller composes into its own view would let the caller's bindings fire inside the browser and would mix two action types; scoping bindings per body would have been a second keymap model. A foreground handoff that keeps the alternate screen would still stop the opener's painting and lose the opener's state on the way back; nesting keeps both.
