# Feedback and state transitions

A notice should name the state, explain its consequence, then offer a useful next step. [Banner](../../src/components/feedback/banner/banner.tsx) accepts a `heading` independently of the native `title` attribute and an `actions` slot after its body. [Callout](../../src/components/editorial/callout/callout.tsx) keeps its editorial heading and optional eyebrow, with actions after the context. Both retain a named visible tone glyph when artwork is omitted. A custom glyph supplements the tone's accessible name.

Banner defaults to an alert for danger and a status for other tones. Static editorial context belongs in Callout's non-live note; override Banner's `role` when a consumer owns the announcement region. A composed operation should have one persistent live region, a stable region name and useful context, and a trigger that remains where the reader left it. [Progress](../../src/components/feedback/progress/progress.tsx) supplies task semantics without a live region of its own.

[The Banner examples](../../src/components/feedback/banner/banner.examples.tsx) demonstrate a consumer-owned file review through waiting, success, failure, and retry. Their timer is a bounded Catalogue fixture, not package behaviour or a state-machine API. The persistent Banner announces one state update, while a separate Progress slot reserves its space and leaves the accessibility tree when idle. The status area reserves enough local height for the outcome; consumers must size that reserve against their own text and allocations. The trigger remains focusable and ignores repeated activation while pending. The fixture deliberately does not set Button's `busy` or `aria-busy`, which disable native activation and remove its tab stop. It never restores focus after the reader moves elsewhere.

[EmptyState examples](../../src/components/feedback/empty-state/empty-state.examples.tsx) distinguish first use, no search results, unavailable content, and a recoverable load failure. Ordinary empty content does not need an error tone or a live announcement. The existing title, description, icon and actions API is sufficient; consumers choose content and real destinations or handlers.

[Focused browser checks](../../tests/feedback_state_transitions_test.tsx) cover long-content containment, tone witnesses with omitted/custom artwork, single outcome mutation, persistent nodes, keyboard focus and retry. The review postures use the existing instrument's click action to start the live Reel; its synchronous assertions do not wait for asynchronous outcomes or emulate native Enter activation. Real keyboard and timed assertions live in the browser test. DOM evidence establishes announcement structure and update count; screen-reader speech remains dependent on the consumer and assistive technology.
