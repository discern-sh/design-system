# Codegen

How [`generate.ts`](../../scripts/generate.ts) turns Component Metadata, kind-family Metadata, and package assets into committed authorities under [`src/generated/`](../../src/generated/). The Catalogue's ignored example registry is a build output: [`build.ts`](../../scripts/build.ts) regenerates it under `catalogue/generated/` before bundling or verification consumes it.

`generateOutputPlan()` is the committed artifact inventory: it names every byte written beneath the wholly owned `src/generated/` and `scripts/generated/` roots. `writeGeneratedSources()` serializes concurrent invocations, plans the complete reconciliation before changing disk, removes every entry absent from that inventory (including ignored dotfiles such as `.DS_Store`, nested OS debris, and abandoned old outputs), and atomically replaces only changed files. `[generated.codegen]` in [`discern.toml`](../../discern.toml) binds those roots and `deno task codegen` into discern's refresh, drift, merge-regeneration, and GitHub Linguist handling. [`generated_sources_test.ts`](../../tests/generated_sources_test.ts) guards the complete-tree and plan-before-effect boundaries; the general generated-source currency assertion consumes the same output plan, so a newly enrolled output cannot miss its drift guard.

Kind codegen is a family framework: [`kind-family.ts`](../../scripts/kind-family.ts) owns discovery, anatomy/stance/corpus validation, and generation for any enrolled kind family, and a family is a configuration — its lowercase word and Pascal type stem (which derive every generated symbol name, error-code template, and message), kind root, budget-remedy, release-posture, and CLI-stance vocabularies, generated file names, and the module specifiers its generated sources import. Two families are enrolled: the diagram family under [`src/diagram/kinds/`](../../src/diagram/kinds/) and the chart family under [`src/chart/kinds/`](../../src/chart/kinds/), each as a configuration in `generate.ts`, never by copying the machinery. A family's terminal projector surface is one optional configuration group; both families now declare theirs, so each gets a generated callable CLI registry (`diagram-cli-registry.ts`, `chart-cli-registry.ts`) and the two-way stance pairing makes a missing kind projector — or an orphan `*.cli.ts` beside a description-only stance — a generation failure. A family without a declared surface still records each kind's stance at birth while rejecting kind CLI modules outright, the posture the chart family shipped from.

Each folder under a family's kind root has one fixed anatomy and one `*.meta.ts` enrollment fact. The framework validates that anatomy, guidance, numerical budgets, deeply frozen release corpus, and the family's CLI stance rules — description-or-enhanced for both families, with a per-family hook enforcing the chart honesty tier beside its enhanced stance — before emitting the authored spec union, the distinct normalized union returned by validation, public Metadata and Markdown author guide, exhaustive semantic dispatch, fixture/corpus registry, type export barrel, and (for a family with a declared terminal surface) the CLI registry together. Every corpus must cover the family's declared postures — the diagram set of minimal, representative, structural, long-text, maximum-density, and semantic-role, which the chart family extends with quantization-edge and formatter-table — plus invalid cases and an over-budget refusal whose dimension and remedy agree with Metadata; Catalogue and CLI examples derive from the same specs. Generated dispatch is the only projection switch; kind implementations and callers never patch it. The shared harness in [`tests/kind_family_harness.ts`](../../tests/kind_family_harness.ts) fabricates synthetic future kinds and malformed inventories for [`tests/diagram/generator_test.ts`](../../tests/diagram/generator_test.ts) and [`tests/chart/generator_test.ts`](../../tests/chart/generator_test.ts), so adding a kind cannot silently omit a projection or release posture and a new family cannot fork the machinery.

Component codegen reads the fixed folder anatomy through `loadComponentSources()` — Metadata, stylesheet, implementation, examples, the example vocabulary, and the CLI stance pairing — and emits the Runtime Registry, the React and CLI barrels, the CLI stance registry, the review-tool example registry, and the public Metadata module `component-metadata.ts`, whose `componentAuthorGuide` [`component-author-guide.ts`](../../scripts/component-author-guide.ts) renders from the same sources. The `use-discern-design-system` skill's eval set is the third wholly owned generated root: [`component-author-evals.ts`](../../scripts/component-author-evals.ts) projects each Component's first use-when and first refusal into prompts under [`skills/use-discern-design-system/evals/`](../../skills/use-discern-design-system/evals/), and `[generated.codegen]` lists that root beside the two source roots. [`component_author_guide_test.ts`](../../tests/component_author_guide_test.ts) and [`component_author_evals_test.ts`](../../tests/component_author_evals_test.ts) enrol a synthetic future Component in both projections and prove every eval's reference image is a committed file.
