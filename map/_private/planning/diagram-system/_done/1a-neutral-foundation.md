## Background

The design system currently frames caller-owned diagrams through `DataFigure` and treats Markdown images semantically, but it has no package-owned diagram model, layout, SVG emitter, or terminal projection. The reference repository that prompted this work creates attractive static SVG by teaching an agent a constrained visual grammar; it does not provide a reusable engine. External tools each trade away at least one binding requirement: deterministic bytes, live token theming, accessible text, a React-free neutral graph, portable standalone SVG, or a meaningful terminal edition.

The foundation therefore owns a small typed system. Authors state relationships and limited semantic emphasis. A kind validates and lays that meaning into a closed internal `DiagramScene`; a shared conformance pass then proves the universal geometry promises before any projection sees it. Every projection consumes that scene or the original validated semantics; no projection reverse-engineers another. The initial flow implementation is intentionally optimised for documentation-scale reference diagrams rather than arbitrary graph visualisation or intuition-building interactive explainers.

## Fixed foundation contracts

- Specs are recursively readonly, JSON-safe data. They contain no React nodes, functions, Dates, DOM objects, class names, CSS, SVG snippets, ANSI, callbacks, or layout-engine objects.
- Every spec carries a non-empty accessible title and summary. One canonical short alternative is derived from both for image/Markdown naming, while the fuller structural description preserves topology. Labels are plain text. Meaning-bearing IDs are stable printable ASCII identifiers.
- The common pipeline remains `validate → kind layout → DiagramScene`; kind layout includes one shared package-private post-layout conformance pass and cannot return until universal bounds, clearance, attachment, and intersection invariants pass. `describeDiagram` dispatches through the same generated kind authority and preserves every semantic fact that a terminal reader needs.
- `DiagramScene` is a closed, immutable, projection-neutral geometry vocabulary. It contains finite coordinates and semantic style roles, never token values, CSS strings, JSX, terminal glyphs, or raw XML.
- Equal input and options produce equal scenes and descriptions. Ordering, tie-breaks, numeric precision, whitespace, limits, font-metric data, and failures are deterministic. A complexity refusal names the exceeded budget and a practical author remedy rather than returning a generic failure.
- Kind enrolment is a canonical generated set. Every kind declares its metadata, concise use/not guidance, measurable complexity budget, and terminal stance at birth. A description implementation is mandatory; an enhanced CLI implementation is optional and paired mechanically with the stance.
- Waves 1–5 use only repository code and platform primitives. Do not add an import, package, binary, WASM module, vendored engine, copied font parser, or generated third-party asset.

Link it from a new `map/25-diagrams/README.md` that explains the present subsystem boundary and where future maintainers start, without restating derivable inventories.
2. **Define the neutral contracts under `src/diagram/`.** Add a small coherent module family for common spec facts, accessibility, validation errors and limits, scene primitives, kind metadata, and internal dispatch types. The eventual public entrypoint will be `src/diagram/mod.ts`, but do not add it to `deno.json` or `package.json` in this wave. Settle names in the ADR and tests; prefer `DiagramSpec`, `DiagramScene`, `DiagramKindMeta`, `diagramAltText`, and `describeDiagram` unless the live code supplies a stronger convention. `diagramAltText` must derive one concise useful image alternative from title and summary; it is not a second authored field. Budget errors must carry stable codes/facts and say whether the author should shorten a label, reduce one tier, or split overview from sub-flow. Keep the scene union only as rich as the first vertical slice proves—boxes/shapes, text with conservative bounds, connectors/paths, arrowheads or equivalent geometry, grouping/order, and canvas bounds—rather than predesigning a general graphics API.
3. **Create a fixed kind anatomy and generated registry.** Establish `src/diagram/kinds/<kind>/` with an explicit required file set for metadata, spec/types, validation/layout, description, fixtures/examples, and `mod.ts` (the exact split may be smaller when one file remains the single authority). Metadata owns concise `useWhen`/`notWhen` guidance following the existing Component convention, measurable kind budgets, and CLI stance so author documentation and validation cannot drift. Extend `scripts/generate.ts` so it discovers kind Metadata, validates unique slugs/order, validates required modules, and validates `cli: { stance: "description" }` versus `cli: { stance: "enhanced" }` plus the presence or absence of the kind's enhanced CLI module. Generate the registry, discriminated `DiagramSpec` union, exhaustive dispatch, and any public re-export needed by wave 2 into `src/generated/`; never hand-author a parallel list. Add generator tests that fail for an unenrolled kind, incomplete authoring/budget metadata, missing description, mismatched enhanced stance, duplicate identity, or orphan enhanced module.
4. **Implement the first `flow` semantic grammar.** It must represent documentation-scale directed processes with stable node IDs, concise primary labels, optional secondary annotations, restrained semantic node roles (including ordinary step, decision, and start/end), directed labelled edges, primary/secondary/return emphasis, and top-to-bottom or left-to-right direction. Main-flow edges establish a deterministic layered order; explicitly marked return edges may close a loop and route outside the primary flow. Reject unsupported cyclic primary graphs rather than drawing nonsense. Do not add clusters, free-form ports, icons, arbitrary shapes, per-item colours, or x/y coordinates—the later `architecture` and `cycle` kinds own those semantics.
5. **Build a dependency-free flow layout and prove its scene.** Use a documented, deterministic layered algorithm suited to roughly 5–15 nodes: validate first, measure/wrap labels with an explicit repository-owned approximation and conservative padding, assign ranks and stable within-rank order, size nodes, route connectors, place edge labels, and compute a tight padded view box. Bind any committed bundled-font measurements to the inspected font bytes, following the existing font-metric authority; keep conservative script/grapheme-class fallback data for other fonts. Browser measurement may live in a separate reproducible calibration or conformance path, but never in runtime layout or routine codegen. After layout, run one shared package-private conformance authority that proves finite positive bounds; text, annotation, and arrowhead containment/clearance; connector attachment at actual shape boundaries; and no connector crossing an unrelated node or label. Lines must stop at boundaries rather than pass behind an occluding fill. Source order may be a declared tie-break but must never replace semantic graph validation. Route return edges clearly outside the primary ranks. Keep layout arithmetic independent of palette and renderer. Reject non-finite output, excessive complexity, impossible labels, a conformance defect, or a graph beyond the recorded bounds before returning a partial scene.
6. **Make the visual grammar data-driven but small.** Define semantic scene roles such as canvas, node surface/border/text, quiet annotation, accent/focus, success/warning, primary/secondary/return connector, and optional guide. Do not resolve them to CSS variables or colour values here. Establish consistent geometry constants—spacing rhythm, radii, line weights, arrowhead proportions, text sizes, and density limits—from one authority rather than distributing numbers across the kind. Use the existing 4px token rhythm as a design input without importing CSS presentation into layout.
7. **Implement both accessibility projections.** `diagramAltText(spec)` validates through the same boundary and returns a stable concise title+summary alternative suitable for ordinary Markdown images. `describeDiagram(spec)` emits stable plain text containing that accessible context followed by the kind's meaningful ordered entities and relationships. For flow, distinguish start/end, decisions, branch labels, primary progression, and return edges without relying on colour or arrow glyphs. It must not silently omit secondary annotations. Use ordinary Unicode-independent text so it remains meaningful in ASCII/no-colour terminals and raw logs; terminal styling belongs to 2A.
8. **Prove the authority and algorithm.** Add focused tests, preferably under `tests/diagram/`, for valid minimal and representative flows, branching decisions, labelled edges, left-to-right direction, return edges, disconnected or invalid graphs, duplicate and dangling IDs, empty/hostile/control-bearing labels, maximum limits, long wrapping labels across representative Latin, wide-script, combining, and mono-annotation cases, deterministic reruns, stable numeric rounding, actionable budget errors, and exhaustive description facts. Assert scene invariants: finite coordinates, positive/tight bounds, nodes do not overlap, connector bodies cross no unrelated node or text bounds, connectors attach at node boundaries without fill occlusion, arrowheads and text retain the declared clear space, all geometry lies inside the view box, and primary labels fit the layout's declared boxes. Add a graph/import guard showing the neutral diagram modules resolve neither React nor external runtime packages.
9. **Leave future kinds no manual checklist.** Add a test fixture or generator harness proving that placing one conforming kind in the canonical source tree enrols its spec union, metadata, description/layout dispatch, CLI stance, and generated exports together. A new kind must make typecheck or codegen fail until every mandatory surface is present; no catch-all branch may silently ignore an unknown kind.

## Constraints

- Keep this wave internal: no `./diagram` package export, React Component, CSS, standalone SVG serializer, terminal frame renderer, Markdown prop, Catalogue surface, version bump, release, or consumer edit.
- Do not copy layout code from Dagre, Graphviz, ELK, Mermaid, D2, the reference repository, or Discern's marketing artwork. If an algorithmic idea is informed by a source, implement it independently and record provenance where it materially shaped the result.
- Validation is a complete preflight. No renderer may receive hostile strings, duplicate IDs, dangling references, unsupported primary cycles, excessive depth/count, or non-finite geometry.
- Do not expose `DiagramScene` as a caller-authored escape hatch merely because tests need it. If test helpers require access, keep them package-private unless wave 2 proves a stable public use.
- Preserve the design principles: one authority per fact, generated membership, framework-neutral core, deterministic output, token-only theming, and accessibility as a tested contract.
- After the final edit, run `discern_prepare`, commit the resulting clean tree, then run `discern_done` once on committed HEAD. Fix diagnostics at their owning authority; never loosen a standard to pass.

## Out of scope

- React or HTML rendering, SVG/XML serialization, DataFigure composition, Catalogue preview, or Markdown integration.
- Enhanced terminal box drawing; only the neutral lossless description and stance mechanism are established here.
- Kinds other than `flow`, a public plugin/custom-kind API, stateful editing, animation, zoom/pan, links, icons, images, gradients, arbitrary ports, mathematical notation, or rich text labels.
- Font parsing, embedded/subset fonts, browser/DOM measurement in runtime layout or routine codegen, general graph layout, or any dependency evaluation beyond preserving the zero-dependency baseline. A separate browser calibration/conformance probe may audit committed conservative metric data without becoming its generation authority.
- Editing or releasing the sibling Discern product.

- **Measurable:** the diagram architecture ADR is accepted and linked from `map/25-diagrams/README.md`; one generated kind authority enrols a dependency-free `flow` spec, authoring/budget metadata, layout, description, fixtures, and CLI stance; invalid anatomy fails generation; committed font-metric data remains deterministic and independently auditable; actionable budget errors and shared post-layout scene conformance guard bounds, label/arrowhead clearance, connector attachment/intersections, validation, safety, description, import boundaries, and future enrolment; `discern_done` is green on clean committed HEAD.
- **Semantic:** a later projection can receive a small real documentation flow and trust that its meaning has been validated, laid out once into stable geometry, and expressed losslessly in text without knowing anything about React, SVG, terminal bytes, or a third-party engine.
