## Background

The dataviz programme adds charts as a sibling kind family beside the five landed diagram kinds — the programme README records why charts cannot be diagram kinds. Before any chart code exists, two duplication traps must be removed from the landed tree. First, the kind codegen hardwires one family: `loadDiagramKindSources` (`scripts/generate.ts:417`) and `generateDiagramKindSources` (`scripts/generate.ts:740`) already take a kind-root URL (the generator tests pass temporary roots), but everything else — the `Diagram` naming, the spec/validated union shapes, the six generated file names, the release postures, the CLI stance registry, the author guide, the error messages — is baked in, so a chart family would need a second generator that repeats all of it. Second, roughly a dozen family-neutral authorities live under `src/diagram/`, where a chart module could reach them only by importing diagram internals (the cross-family coupling the design principles forbid) or by copying them (a second authority for the same fact).

`scripts/generate.ts` (1192 lines) has two halves: component/asset codegen and the diagram kind machinery (inventory validation at `:180-308`, source loading at `:417`, generation at `:740-1050`, composed into `generateSources`/`writeGeneratedSources` near the end). The kind half emits six files into `src/generated/`: `diagram-spec.ts`, `diagram-metadata.ts` (metadata plus `diagramKindAuthorGuide`), `diagram-registry.ts` (fixtures and release corpora), `diagram-dispatch.ts`, `diagram-exports.ts`, and `diagram-cli-registry.ts`. `tests/diagram/generator_test.ts` (381 lines) proves the machinery future-enrolling with ten guards (lines 135–368) driven by a synthetic-kind harness (`writeKind`/`withTemporaryRoot`, lines 31–133) that fabricates conforming and malformed kind folders in temporary roots.

## The refactor invariant

This invariant is absolute; a violation is a failed wave, not a judgment call.

- Every file under `src/generated/` regenerates byte-identically: after the refactor, `deno task codegen` followed by `git diff -- src/generated` shows nothing. Note the generated banner reads `/* Generated by scripts/generate.ts. Do not edit. */` — byte-identity therefore constrains the factoring: whatever module structure you choose, `scripts/generate.ts` remains the entry point the banner names, or the banner's authority is preserved without changing a byte.
- The entire existing test suite passes unmodified. The only test file you may edit is `tests/diagram/generator_test.ts`, and only to extend it; every other existing test file stays byte-identical. New test files may be added where the family framework needs coverage the generator test cannot express, but prefer extending the harness that exists.
- The public API surface is unchanged: `tests/release_test.ts` is untouched and green, and no export of any `deno.json` entrypoint changes name, type, or behaviour.
- Every promotion is a move-with-re-export, never a copy. Each promoted module leaves a facade at its current `src/diagram/` path re-exporting the exact existing names, so no existing import — source, test, or public — changes. Grep proves each promoted implementation exists exactly once in the tree.

Two constraints were pre-verified during planning so you need not re-litigate them, only re-confirm: the `./diagram` neutrality guard in `tests/release_test.ts` ("the published diagram graph is neutral, local, and permission-free") asserts `file://` locality and rejects `/src/cli/`, `.tsx`, `.fixtures.ts`, and any specifier matching `react` case-insensitively — it does not assert directory membership, so a shared internal root passes provided its path avoids those patterns; and `deno.json` `publish.include` already covers all of `src/`, so no allowlist change is needed.
