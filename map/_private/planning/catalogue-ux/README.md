# Catalogue UX programme

Briefs for turning the design-system Catalogue into a quiet, highly visual reference that people can navigate by recognition and spatial intuition. The programme keeps the generated, source-backed integrity of the current Catalogue while removing the machine-oriented language, duplicate directories, long mixed-purpose pages, hidden affordances, and cross-surface drift that make it feel like an implementation report rather than a catalogue.

The findings behind this programme came from browsing every major Catalogue route in a real browser and then tracing the visible behaviour back to its authorities. Two facts determine the work shape:

- `catalogue/app.tsx` is currently 2,008 lines and `catalogue/catalogue.css` is 1,703 lines. Page redesigns cannot safely run in parallel until the shared shell, routes, pages, and styles have real ownership seams.
- All 109 CLI-rendered Components currently expose a different Web and CLI example sequence. Example parity is therefore a repository-wide contract migration with a future-member guard, not a presentational patch in one page.

Every brief is a self-contained prompt for a fresh agent. This is an independently landed wave programme, not a below-trunk branch stack. Dispatch a wave only after every lower wave has landed on `main`. Briefs in the same wave run concurrently in separate worktrees and own disjoint files. Within a wave, land in the order shown; later streams call `discern_update`, re-read any overlap discern names, and run their final gate against the composed trunk.

## Fixed programme contracts

Change one only through a justified programme amendment, and use an ADR when the choice is architectural or hard to reverse.

| Fact                   | Contract                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product posture        | The Catalogue first feels like a catalogue: previews, specimens, swatches, and recognisable destinations lead; explanatory material supports them quietly. It must not become an instruction manual or make users read prose to understand where to go.                                                                                                                                              |
| Guidance density       | Component usage guidance and API material remain closed by default. The visual specimen is primary. A redesign may make supporting material easier to find, but it must not expand every “Best practices”, selection, or props disclosure into the normal page flow.                                                                                                                                 |
| Navigation order       | One route authority supplies the same human-facing order everywhere: **Overview, Components, Foundations, Compositions, Terminal layouts, Compare**. The stable `/catalogue/review/` URL may remain for compatibility while its visible task language becomes “Compare”.                                                                                                                             |
| Human language         | Visible copy describes a person's task. Internal phrases such as “mount complete contracts”, “generated destination”, “explicit scope”, and “surface inventory” appear only where provenance itself is the subject. Action labels say what happens: Find, View, Compare, Copy, Open source, or Change appearance.                                                                                    |
| Progressive disclosure | Index routes stay light and help people choose. Detail routes show one bounded subject. Exhaustive evidence remains available, but is secondary and explicitly labelled as comparison or quality-assurance work.                                                                                                                                                                                     |
| Cross-surface examples | Every rendered Component owns one precise, ordered example vocabulary. Web and CLI use the same stable id, human label, and relative order whenever the semantic posture can exist on both. A surface-only example is allowed only when the other surface literally cannot represent the fact without lying, and carries a specific non-empty reason. Silent divergence is a build failure.          |
| Example naming         | Stable ids are kebab-case and semantic rather than surface-prefixed. Human labels come from the same authority. `default`, when present, is the representative baseline and comes first; variants, lifecycle states, and stress/fallback evidence follow in a deliberate stable order. Capability facts belong in capability data unless the changed capability is itself the scenario under review. |
| Composition status     | Compositions are **illustrative patterns**: a grouped collection of high-quality demonstrations from which consumers draw inspiration. They are not a second package API and must not be described as exported Components or guaranteed copy-paste recipes. Source may be inspectable and copyable when useful, but its label must state that it is adaptable example source.                        |
| Overflow cue           | The scroll/fade affordance becomes a public, reusable `OverflowCue` Component with a framework-neutral emitted behaviour, not Catalogue-only CSS or a React-only hook. It works on block and inline overflow, logical start/end edges, dynamic content, resize, keyboard scrolling, themes, RTL, reduced motion, and touch without hiding native scrolling.                                          |
| Appearance             | Theme and accent hue belong to one compact Appearance control. The accent range must not read as an unexplained piece of primary toolbar chrome. Appearance state remains persistent and URL-reproducible where review work needs it.                                                                                                                                                                |
| URL state              | Shareable state belongs in the URL: routes, collection/filter state, selected Component example and surface, comparison scope, terminal capabilities, and bounded explorer choices. Local storage may remember comfort preferences, but must not be the only way to reproduce a review.                                                                                                              |
| Accessibility          | Every route has one clear `h1`, a working skip link, sound landmark and heading structure, visible focus, keyboard-complete controls, and no document-level horizontal overflow. Modal search and mobile navigation trap/restore focus and lock the background correctly.                                                                                                                            |
| Muted metadata         | This programme deliberately does **not** perform the proposed pass to raise the prominence of muted explanatory text or tiny metadata. Preserve current token choices unless a specific control is illegible or fails accessibility; that nuanced visual pass belongs to a later workstream.                                                                                                         |
| Interface Builder      | `catalogue/builder/**` is out of scope. Do not browse, redesign, or add dedicated Interface Builder tests. Never weaken or skip the full project gate merely because existing conformance happens to exercise it.                                                                                                                                                                                    |
| Public landing         | The site root and Catalogue overview are two front doors to the same system. Both use the canonical route order, make “Find a Component” conspicuous, expose long-page navigation where needed, and direct people to bounded Catalogue destinations rather than generic “browse everything” calls.                                                                                                   |
| Generated facts        | Metadata, Tokens, Component registries, CLI stances, composition definitions, and terminal foundation registries remain the facts. UI projections may reorganise them but never create parallel hand-maintained counts, names, source paths, or membership lists. Generated files are never hand-edited.                                                                                             |
| Release posture        | Catalogue-only work does not bump or publish a version. A public Component, behaviour, type, or contract change receives an Unreleased changelog entry. Publishing remains a later owner-run `release` skill task.                                                                                                                                                                                   |

Wave 1 intentionally lands alone. It replaces the monolithic page and stylesheet boundaries with route-family modules and page-owned styles, so later workstreams can be genuinely parallel instead of editing different regions of the same two files.

Wave 2 is the repository-wide example contract migration. It can fan out internally across disjoint Component Group bundles after its coordinator has committed the shared authority, but it lands as one coherent branch. No page stream designs against an example contract that is still moving.

Wave 3 is the five-way UI fan-out. Every stream starts from the landed architecture and example contract. `3D` is the only wave-3 generated-surface owner because it adds a public Component and uses it immediately in the Terminal lab. Implementations run concurrently, then land in key order (`3A` → `3B` → `3C` → `3D` → `3E`); each later branch brings the already-landed trunk beneath its work with `discern_update` before its final proof. The final integration pass adopts `OverflowCue` in front-door or other page-family overflow locations only after those page branches have landed.

Wave 4 is a convergence and hardening pass, not a licence to redesign everything again. It inspects the live pages with human eyes, fixes cross-page inconsistencies, strengthens real-browser guards, and brings the Catalogue map up to date.

## Acceptance matrix

The final integrated experience must let a person do these tasks without learning implementation vocabulary:

| Task                     | Expected route and outcome                                                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Find a known Component   | Global search or `/catalogue/components/` reaches the detail page directly and explains why a search result matched.                                                                                  |
| Browse by recognition    | Group and purpose cards show recognisable names, labelled counts, an obvious click affordance, and a compact `+N more` summary rather than prose-heavy descriptions.                                  |
| Inspect one Component    | The specimen and named example control lead. Web/CLI switching preserves the same example identity and URL. Guidance, selection, and API evidence remain closed, orderly, and secondary.              |
| Compare a collection     | A Group, purpose, or custom selection opens one comparison workspace with a jump list, set-all Web/CLI actions, resettable per-Component overrides, and no duplicated directory or heading hierarchy. |
| Inspect a Token          | Search/filter reaches a bounded visual Token view with copy actions and truthful light/dark or single-value evidence.                                                                                 |
| Learn from a Composition | The index describes it as an illustrative pattern; detail shows an isolated responsive demonstration, constituent Component links, and clearly labelled adaptable source.                             |
| Test a terminal layout   | A bounded recipe lab chooses a preset, overrides real capabilities, sees raw frame/overflow facts, scrolls with visible edge cues, copies output or source deliberately, and can share the URL.       |
| Use a narrow screen      | The page never scrolls horizontally at document level, the drawer behaves modally, wide specimens scroll locally with `OverflowCue`, and all actions remain reachable by keyboard and touch.          |
| Move between front doors | The root landing page and Catalogue overview use the same route order and destination names, with a conspicuous Find a Component path and useful in-page navigation.                                  |

## Landing authority

Every stream stops for owner review unless discern records a grant. After `discern_done` passes on the final committed tree, the agent runs `discern_accept`. A standing or per-worktree grant may land it; without one, the verb refuses without mutation and the agent reports the proof line plus branch/worktree for review. Prose in these briefs is never landing authority.

The planning package follows the same rule and must land before `catalogue-1a` is dispatched, because each implementation stream moves its own committed brief into `_done/` as part of its final commit.

## Adversarial review loop

When a stream reports green, review its branch diff against `main`, hold every deliverable to the semantic goal as well as the checklist, rerun the gate in its worktree, and open its exact preview URL. Before dispatching the next wave, re-read the unstarted briefs against what actually landed and amend stale anchors.

Look especially for:

- a reshuffle of code that leaves page modules coupled through one shared state or stylesheet;
- a new hand-maintained navigation, count, example label, or membership list beside an existing authority;
- “parallel” streams drifting into a sibling's files;
- Web/CLI parity achieved by vague names, giant catch-all examples, or unjustified surface-only exceptions;
- all supporting disclosures expanded in the name of discoverability;
- a bespoke fade in one page instead of the public `OverflowCue` contract;
- a cue that signals overflow but breaks keyboard scrolling, touch, RTL, resize, themes, or reduced motion;
- a Composition presented as package API or guaranteed copy-paste code;
- Review surviving as a second duplicate Component directory under a new label;
- filter, surface, example, or capability state that cannot be linked;
- visual fixes that merely darken all muted metadata, contrary to the explicit deferral;
- source-string tests that pin an implementation shape while missing the user behaviour;
- generated files hand-edited, tests loosened, or a consequential decision left outside an ADR.

After 4A lands and passes adversarial review, the Catalogue workstream is ready for owner prioritisation of any remaining nuance and a separate muted-metadata pass if still wanted.
