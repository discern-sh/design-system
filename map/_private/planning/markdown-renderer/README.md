# Markdown renderer programme

Briefs for making Markdown a first-class, component-backed rendering surface in `@discern-sh/design-system`, with a faithful terminal edition and a semantic browser edition. The programme follows a repository-wide inventory made on 2026-08-15: the generated CLI registry had 121 Components, 100 rendered and 21 reasoned-exempt, but no generic Paragraph, List, Blockquote, Code block, or top-level Markdown Component. The existing Prose, Heading, Table, Pull quote, Code listing, and Footnotes renderers cover adjacent presentation needs without together forming a lossless Markdown vocabulary.

The flagship Discern consumer already carries a hand-built, deliberately incomplete Markdown renderer in `/Users/jack/Sites/discern/src/lib/markdown.ts`. Its source and `/Users/jack/Sites/discern/tests/markdown_test.ts` are read-only compatibility evidence for this programme: they prove the real need for headings, paragraphs, inline emphasis and code, links, images, rules, fenced code, ordered/unordered/task lists, nested content, blockquotes, GitHub alerts, GFM tables, width-aware wrapping, HTML escaping, ASCII/no-colour degradation, and hostile-control handling. This package programme does not edit or adopt the consumer.

Every brief is a self-contained prompt for a fresh agent. Dispatch one wave only after every lower wave has landed on `main`. Waves 2 and 3 ask their coordinating agent to fan out disjoint Component folders inside one worktree when sub-agents are available. They deliberately do not use parallel worktrees: all new Components enrol through the same generated registries and Catalogue surfaces, so separate branches would merely relocate collisions into integration.

## Fixed programme contracts

Change one only through an explicit ADR and an update to every unstarted brief.

| Fact                  | Contract                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Programme goal        | A consumer can pass Markdown source to the public Markdown Component and receive deterministic, width-aware terminal output or safe semantic browser output, with all supported syntax routed through package Components and authorities.                                                                                                                                                                      |
| Syntax                | CommonMark plus GFM tables, task-list items, strikethrough and autolinks; GitHub-style `[!NOTE]`/`[!TIP]`/`[!IMPORTANT]`/`[!WARNING]`/`[!CAUTION]` alerts; and footnotes. Reference links, escaped punctuation, entities, soft/hard breaks, setext and ATX headings, indented and fenced code, nested block structures, and ordered-list starts are included.                                                  |
| Safe HTML posture     | Source HTML is never executed. HTML comments do not render; other raw HTML is preserved only as inert escaped/literal text. No `dangerouslySetInnerHTML`, terminal control passthrough, or caller-authored ANSI.                                                                                                                                                                                               |
| One parsing authority | One shared parser/adapter produces the same package-owned neutral tree for either the React or CLI projection; separate render calls may each parse their source, but the two editions never maintain different grammars or models. Do not leak a third-party parser's AST through the public API.                                                                                                             |
| Component composition | Paragraph, List, Blockquote, Code block, Heading, Divider, Table, Callout, and Footnotes own their semantics and presentation. Markdown dispatches to them; it does not copy their frames, CSS, palette, glyphs, width algorithms, or vertical rhythm. Pull quote, Code listing, Checkbox, Procedure, Prerequisite list, and Key points retain their more specific semantics and are not Markdown substitutes. |
| Inline content        | Inline semantics are represented as typed data, never pre-authored ANSI: text, emphasis, strong, strikethrough, inline code, link, image fallback, soft/hard break, and footnote reference. The CLI projection uses the published styled-text and hyperlink authorities.                                                                                                                                       |
| Fidelity              | No source content is silently truncated. Narrow output wraps or chooses a documented lossless stacked form. Code may visibly wrap with a continuation treatment, but no code characters or logical blank lines disappear.                                                                                                                                                                                      |
| Degradation           | Truecolour, ANSI 256, ANSI 16, no-colour, Unicode, and ASCII output carry the same facts. Plain output keeps structural markers where styling alone would otherwise erase meaning.                                                                                                                                                                                                                             |
| Compatibility         | Existing public string props and their default exact frames remain valid. Rich/lossless behaviour is additive unless an ADR explicitly records a breaking change.                                                                                                                                                                                                                                              |
| Parser dependency     | Prefer a maintained, spec-oriented parser over a hand-written grammar. Pin it through `deno.json`, keep the published graph React-free, document its dialect/security policy in an ADR, and expose only package-owned types.                                                                                                                                                                                   |
| Versioning            | No implementation brief bumps package versions or publishes. Each adds a CHANGELOG entry under **Unreleased**; the owner uses the `release` skill after wave 4.                                                                                                                                                                                                                                                |
| Worktree names        | Pass these literal names to `discern_start`: `markdown-1a`, `markdown-2a`, `markdown-3a`, and `markdown-4a`.                                                                                                                                                                                                                                                                                                   |

This is an independently landed sequence, not a below-trunk branch stack. Do not dispatch a higher wave early. Each higher-wave brief has a trunk dependency guard and starts a normal worktree from the then-current `main`; no branch-name placeholder or manual relay is required.

## Landing authority

Every wave changes the published package and stops for owner review unless discern records a grant. After a clean committed `discern_done` proof, the agent runs `discern_accept`. A standing or per-worktree grant may land it; without one, the verb refuses without mutation and the agent reports the proof line and branch/worktree for review. Prose in a brief is never landing authority.

Within the component-heavy waves, the coordinating agent owns commits, generated surfaces, map updates, CHANGELOG, the Catalogue server, the final gate, and acceptance. Its sub-agents edit only assigned source/test slices in the same worktree and do not dispatch other briefs or land anything independently.

## Review loop

When a wave reports green, review its branch diff against `main`, verify every deliverable and compatibility promise, run the gate against that worktree, inspect the exact frames and Catalogue URL, and look especially for duplicated Markdown parsing, raw ANSI or HTML injection, content truncation disguised as responsiveness, hand-edited generated files, loosened exact-frame tests, React entering `./cli`, or domain-specific Components reused under false generic semantics. Re-read the next unstarted brief against the landed API before dispatching it.

Each completed wave moves its own brief into `_done/` in its final commit. After wave 4 lands and the complete programme passes adversarial review, use the `release` skill to choose and publish the appropriate SemVer release. Consumer adoption and deletion of Discern's local renderer are a separate downstream programme.
