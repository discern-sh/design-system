01

What a terminal actually is

The single most useful mental model: a CLI program is not "in" the terminal. It reads and writes streams of bytes through file descriptors, and a separate program — the terminal emulator — interprets those bytes and paints pixels. Everything visual (color, bold, cursor movement, "full-screen" apps) travels in-band, as escape sequences mixed into the same byte stream as the text.

Four layers are involved, and each one owns a distinct job:

terminal emulator iTerm2, Ghostty, Windows Terminal, tmux. Paints pixels, interprets escape codes, turns your keystrokes into bytes.
↕ bytes over a pseudo-terminal (PTY)
tty driver Kernel "line discipline": buffers a line until Enter, echoes typed characters, turns Ctrl-C into a signal. Can be switched off (raw mode).
↕ read / write on fds 0, 1, 2
shell zsh, bash, fish. Parses the command line, expands globs and $VARS, splits words, sets up pipes — then launches your program.
↕ exec with argv + environment
your program Receives an already-parsed argv and an environment. Reads and writes bytes. Never sees quotes, globs, or pixels.

Two consequences GUI developers trip over:

  • The shell owns the command line. By the time your program starts, quoting and glob expansion already happened. There are no quote characters in argv; *.ts either arrived pre-expanded into filenames or (if quoted) as a literal string. When users report "my argument got mangled," the answer is nearly always shell quoting, not your parser.
  • There is no layout engine. The terminal is a dumb grid of character cells. Nothing reflows, centers, or measures for you. Every alignment, wrap, and truncation is your program's arithmetic — which is why width (chapter 07) matters so much.
Carry this

Your program's entire universe is: argv in, environment in, three byte streams, one exit code out. Everything else is convention layered on top of those five things.

02

Streams, pipes & exit codes

Every process starts with three open file descriptors, and the entire composability of the Unix world rests on using them correctly:

fdnamepurpose
0stdinInput. May be a keyboard, a file, or another program's output.
1stdoutData. The program's actual product — the thing worth piping into the next command.
2stderrCommentary. Progress, warnings, errors, log lines — anything a human should see but a pipe shouldn't swallow.

The data/commentary split is the most-violated rule in CLI design and the one users feel first. yourtool list | wc -l should count results — not results plus a banner, a spinner, and a "fetching…" line. Print the product to stdout; print everything about the process to stderr.

Buffering: the classic gotcha

Most runtimes line-buffer stdout when it's a terminal but block-buffer it (≈4–64 KB chunks) when it's a pipe or file. This is why a program prints live in a terminal but sits silent when piped, then dumps everything at exit. If output timing matters — progress, streaming logs — flush explicitly after each meaningful unit.

Exit codes

The one-byte return value is your program's machine-readable verdict, and scripts genuinely branch on it (&&, ||, set -e, CI steps). Zero means success; everything else is failure. A few values carry convention:

codemeaning
0Success — the only success.
1General failure.
2Usage error (bad flags, missing argument) — bash's own convention.
64–78BSD sysexits.h palette (64 usage, 69 unavailable, 70 internal software error…). Optional, but nice for tools others script against.
126Found but not executable.
127Command not found (shell speaking, not you).
128 + nKilled by signal n — Ctrl-C's SIGINT is 2, so 130.

SIGPIPE, or: why head kills you

Run yourtool | head -3 and after three lines head exits, closing the pipe. Your next write triggers SIGPIPE, which by default terminates the process silently — which is correct and desirable! Languages that trap it instead (Node's EPIPE, Python's BrokenPipeError) make you handle it: exit quietly, don't stack-trace. A pipe closing early is the reader saying "I have enough," not an error.

Carry this

stdout is for the next program; stderr is for the human; the exit code is for the shell. Design all three on purpose and your tool composes into pipelines you never imagined.

03

Is anyone watching? TTY detection

A well-behaved CLI is really two programs: an interactive one for humans and a plain one for pipes, scripts, and CI. The switch between them is one question, asked per stream: is this file descriptor connected to a terminal?

environmentcheck
C / POSIXisatty(fd)
Nodeprocess.stdout.isTTY
DenoDeno.stdout.isTerminal()
Pythonsys.stdout.isatty()
Gogolang.org/x/term — term.IsTerminal(fd)
Ruststd::io::IsTerminal — stdout().is_terminal()
Shell[ -t 1 ]

Note "per stream": in yourtool | less, stdout is a pipe but stderr still faces the human — progress on stderr can stay alive while data flows cleanly. In yourtool 2>log, it's the reverse.

What changes when stdout isn't a TTY

  • No color or styling — escape codes become literal garbage like \x1b[32m in files and greps.
  • No spinners, progress bars, or cursor tricks — anything using \r or cursor movement becomes noise.
  • No prompts — never block a pipeline waiting for input nobody can give. If interaction is required and stdin isn't a TTY, fail with a clear message (and offer a flag like --yes).
  • Stable, parseable output — this is the moment users are scripting you; favor one record per line.

The override ladder

Detection is a default, not a verdict. Convention gives users three levers, in rising precedence:

  1. Environment, off: NO_COLOR set to anything means no color (see no-color.org). TERM=dumb means no styling at all. CI often sets CI=1 — many tools treat that as "plain, but keep helpful summaries."
  2. Environment, on: FORCE_COLOR / CLICOLOR_FORCE mean color even when piped — vital because yourtool | less -R and CI log viewers can render color despite not being TTYs.
  3. Flags beat everything: --color=always|never|auto is the user's final word.
Carry this

Ask isatty() once per stream at startup, fold in the env overrides, and pass the result down as a capabilities value. Code deep in your program should never peek at the environment itself — that's what makes output testable (chapter 11).

04

Arguments, flags & environment

Argument syntax is pure convention — the kernel hands you an array of strings — but the conventions are strong, and users' fingers know them:

  • Short flags — -v — single dash, single letter, bundleable: -abc ≡ -a -b -c.
  • Long flags — --verbose — double dash, full words, values as --out file or --out=file.
  • Positional arguments — bare words, order-significant: cp src dest.
  • Subcommands — git commit, deno task — verbs first, each with its own flags. The standard shape for multi-purpose tools.
  • -- ends flag parsing — everything after is positional, even if it starts with a dash. This is how users operate on a file literally named -rf. Honor it.
  • - as a filename conventionally means stdin/stdout.

Every ecosystem has a standard parser that encodes all of this plus help generation — clap (Rust), cobra (Go), argparse (Python), commander/yargs (Node), @std/cli (Deno). Hand-rolling argv loops is how tools end up with flags that can't bundle and no --help.

Configuration precedence

When the same knob can come from several places, the widely-agreed order — most specific wins — is:

  1. Command-line flags (this invocation's explicit intent)
  2. Environment variables (this session/machine)
  3. Project config file, then user config file
  4. Built-in defaults

Environment variables your program should respect

variablewhat it tells you
TERM, COLORTERMTerminal type and color capability (chapter 06).
NO_COLOR, FORCE_COLORStyling overrides (chapter 03).
LANG, LC_ALLLocale and encoding — a value without UTF-8 is a hint to stay ASCII.
PAGER, EDITOR / VISUALWhich pager/editor to launch when you need one. Don't hardcode less or vim.
HOME, XDG_CONFIG_HOME & friendsWhere config, cache, and state belong (~/.config/yourtool/, not ~/.yourtool dotfile sprawl).
COLUMNS, LINESFallback size when there's no TTY to measure (chapter 08).
Carry this

Flags are per-invocation, env is per-session, config files are per-project/user. Use a standard parser, support --, and generate --help — it's the only documentation most users will ever read.

05

Escape sequences: drawing in-band

There is no styling API. To make text green, you print bytes that mean "switch to green" and the terminal obeys until told otherwise. Nearly everything you'll use starts with ESC [ (byte 0x1B then [), called CSI — Control Sequence Introducer — followed by numeric parameters and one final letter that names the command:

\x1b ESC — byte 27, here comes a command
[ CSI — the common introducer
1;38;5;208 parameters, semicolon-separated
m final byte — m = SGR, "set graphic rendition"

That example means "bold, then 256-color foreground 208 (orange)." The m family — SGR — handles all styling. State is sticky: green stays on until you reset it, including after your program crashes. Hence the golden rule: every style you open, you close — usually with \x1b[0m (reset all).

sgr — the styling codes
# style toggles
\x1b[1m  bold    \x1b[2m  dim    \x1b[3m  italic    \x1b[4m  underline
\x1b[7m  inverse    \x1b[9m  strike    \x1b[0m  reset all

# 16-color foregrounds: 30–37, bright 90–97 (+10 for backgrounds)
30 black  31 red  32 green  33 yellow  34 blue  35 magenta  36 cyan  37 white

# deeper palettes
\x1b[38;5;nm       256-color foreground (n = 0–255)
\x1b[38;2;r;g;bm   24-bit truecolor foreground

Beyond styling

The same CSI grammar moves the cursor and edits the screen — the building blocks of progress bars and full-screen apps:

sequenceeffect
\rNot an escape at all — carriage return to column 0. Overwrite the line you're on: the whole trick behind single-line progress.
\x1b[nA / B / C / DCursor up / down / right / left by n.
\x1b[2KErase current line (pair with \r before rewriting it).
\x1b[H · \x1b[2JCursor home · clear screen.
\x1b[?25l / \x1b[?25hHide / show cursor (hide during animation; always restore).
\x1b[?1049h / lEnter / leave the alternate screen — the separate buffer vim and htop use, so quitting restores the user's scrollback.
\x1b]8;;url\x1b\\text\x1b]8;;\x1b\\OSC 8 hyperlink — real clickable links in modern terminals.

You'll rarely hand-write these — libraries and terminfo abstract them — but read them fluently and terminal bugs stop being spooky: mangled output is just literal escape bytes; a vanished cursor is an unmatched ?25l; a "corrupted" shell after a crash is unreset SGR state (fix: reset).

Carry this

Styling is sticky global state written into the output stream. Open-and-close it in the same breath, and on any exit path — including panic — reset styles, show the cursor, and leave the alternate screen.

06

Color & capability detection

Terminals speak four dialects of color, and you can't query which one directly — you infer it. The practical heuristic, checked in this order:

  1. NO_COLOR set, TERM=dumb, or stream isn't a TTY (unforced) → mono.
  2. COLORTERM=truecolor (or 24bit) → 16.7M colors. Most modern emulators set this.
  3. TERM contains 256color → 256 colors: 16 base + a 6×6×6 RGB cube + 24 greys.
  4. Otherwise → assume 16 colors: 8 ANSI hues plus bright variants. Crucially, these are the user's chosen palette — "red" is whatever their theme says red is. Semantic, not literal.

The design discipline that follows: author in semantic roles, not RGB values. Decide that errors are "danger" and highlights are "accent," then map each role down through every depth — truecolor hex → nearest 256 index → nearest ANSI color → bold/plain at mono. The meaning must survive the bottom rung, which also covers colorblind users and screen readers in one move: never encode meaning in color alone. Pair every color with a symbol, word, or weight — ✓/✗, "error:", bold.

truecolor
● api      passing
● worker   failing
● cache    degraded
16-color
● api      passing
● worker   failing
● cache    degraded
mono / ascii
[ok]   api      passing
[!!]   worker   failing
[~ ]   cache    degraded

The same component at three capability levels. Meaning survives every rung because state is carried by symbols and words, with color as reinforcement.

Historically this inference lives in the terminfo database (TERM names a capability record; tput colors queries it). Modern practice leans on the env-var heuristic above — terminfo entries are often stale about truecolor — but it's good to know the formal system exists.

Carry this

Capability detection happens once, at the edge; rendering code receives "depth: mono | 16 | 256 | truecolor" as data. Design palettes as roles that degrade, and let the 16-color tier inherit the user's own theme rather than fighting it.

07

Text width: the hard part

The terminal is a grid, and layout means predicting how many cells a string occupies. The trap: bytes, characters (code points), and cells are three different numbers, and string.length reports none of the ones you need.

d
e
v
終
🚀
é

"dev終🚀é" — 8 cells? No: 6 code points… no: 8 columns — d, e, v (1 each), 終 (2), 🚀 (2), é (1, even when composed as e + combining accent).

The rules, roughly in order of how often they'll bite you:

  • East Asian wide characters (CJK ideographs, kana, hangul) occupy 2 cells. Any table or box containing user text must handle this.
  • Most emoji are 2 cells — and ZWJ sequences like 👩‍💻 are one grapheme built from several code points, which terminals render at inconsistent widths. The safest professional stance: keep emoji out of alignment-critical output.
  • Zero-width characters exist: combining accents, ZWJ, variation selectors all measure 0.
  • A grapheme is the unit users see: truncating by code point can slice an emoji in half or orphan an accent. Truncate by grapheme, measure by cells, and account for the ellipsis: fitting into 10 columns means truncating to 9 + "…".
  • Escape sequences measure 0 — strip ANSI before measuring, or measure before styling. Styling a string then padding it by .length is the classic broken-table bug.

The measuring function is called wcwidth (per code point) in the C world; every ecosystem has a port (string-width in JS, go-runewidth, unicode-width in Rust, @std/cli/unicode-width in Deno). Use a library — the tables are large, versioned with Unicode itself, and full of "ambiguous width" corners (some symbols are 1 cell in Western terminals, 2 in East Asian contexts).

When Unicode itself is a luxury

Check the locale (LC_ALL/LANG containing UTF-8) before emitting box-drawing characters (╭─╮│), and keep an ASCII fallback (+-|) for terminals that can't render them. Same principle as color: design in tiers, degrade without losing meaning.

Carry this

Three different questions: how many bytes (storage), how many graphemes (cursor/truncation), how many cells (layout). Alignment bugs are almost always one of these masquerading as another.

08

Layout in a grid of cells

You get exactly one layout primitive: a W×H grid of cells. Ask the tty for its size (ioctl(TIOCGWINSZ) under the hood; process.stdout.columns, Deno.consoleSize(), shutil.get_terminal_size() at the surface). No TTY? Fall back to the COLUMNS/LINES env vars, then to the ancient default of 80×24 — which survives as a floor: design output to remain legible at 80 columns even if it shines at 160.

  • Wrap on purpose. The terminal hard-wraps mid-word at the last column with no styling awareness. Any line you didn't wrap yourself is a line the terminal will wrap badly.
  • Size can change mid-run. A resize delivers SIGWINCH; long-lived interactive programs re-measure and repaint. One-shot tools just measure at startup.
  • Compose like it's 1975: pad-to-width, truncate-with-ellipsis, join-horizontally, stack-vertically. Those four width-aware operations (built on chapter 07's measurement) are your entire flexbox.
  • Whitespace is your typography. No fonts or sizes — hierarchy comes from blank lines, indentation, alignment, and restrained styling. Consistent two-space indents and aligned columns are the terminal's grid system.
Carry this

Treat width as an input to rendering, never a global you peek at mid-paint — a renderer with the signature (data, width, capabilities) → lines is layout you can unit-test at any size.

09

Input, raw mode & full-screen apps

By default the tty driver runs in canonical (cooked) mode: it buffers a whole line, provides editing (backspace), echoes keystrokes, and turns Ctrl-C into SIGINT before your program sees anything. Perfect for read line prompts; useless for "press any key" or a TUI.

Raw mode (via termios) switches all that off: bytes arrive one at a time, nothing echoes, and Ctrl-C is just byte 0x03 — you now implement quitting. And input has its own escape-sequence problem in reverse: special keys arrive as multi-byte sequences (↑ is \x1b[A) that you must parse, with a genuine ambiguity — a lone ESC byte might be the Esc key or the start of a sequence; only a tiny timeout tells you which. This is why every ecosystem has a key-decoding library; use one.

Signals worth knowing

signalarrives whenyour job
SIGINTCtrl-C (cooked mode)Clean up, exit 130. Catchable for graceful shutdown.
SIGTERMkill, process managersSame as SIGINT, politely.
SIGHUPTerminal closedExit — or finish critical writes first.
SIGWINCHTerminal resizedRe-measure, repaint.
SIGTSTP / SIGCONTCtrl-Z / fgTUIs: restore the terminal on suspend, re-enter raw mode and repaint on resume.
SIGPIPEReader closed the pipeDie quietly (chapter 02).

The shape of a TUI

Full-screen apps (vim, htop, lazygit) all share one architecture, and it will look familiar: it's a game loop, or React for a character grid.

  1. Setup: enter the alternate screen, enable raw mode, hide the cursor.
  2. Loop: read events (keys, resize, timers) → update state → render state to a frame → diff against the previous frame and repaint only changed cells (repainting everything flickers) → write the patch in one flushed batch.
  3. Teardown — on every exit path including panic: show the cursor, disable raw mode, leave the alternate screen. Skipping this is why a crashed TUI leaves the shell unusable-looking (reset recovers it).

Frameworks — ncurses, Bubble Tea (Go), Ratatui (Rust), Textual (Python), Ink (React for CLIs) — own steps 1–3 and the diffing so you write state → view. The state→frame→diff→patch cycle is worth understanding even when a framework does it: it is exactly virtual-DOM rendering, rediscovered for a grid of cells.

Carry this

Interactivity is a mode you enter and must leave: every terminal state you flip (raw mode, alt screen, hidden cursor) is a debt repaid on exit, crash included. Keep the render path pure — events mutate state; state renders to frames.

10

Being a good citizen

The conventions that make a tool feel professional, roughly in the order users will notice:

  • --help and --version always exist, exit 0, and print to stdout. Help shows usage, flags, and a couple of real examples — examples are the part people read.
  • --json (or similar) for machines. Human output is a UI you may redesign freely; the moment people script against it, it's an API you can't change. A machine-readable mode gives scrapers somewhere better to point, and newline-delimited JSON streams well.
  • --quiet and --verbose tune stderr commentary, never stdout data.
  • Errors say what failed and what to do: error: config not found at ./tool.toml — run 'tool init' to create one. Name the file, name the fix, exit non-zero. No stack traces at users (keep them behind --verbose or a debug env var).
  • Destructive actions confirm on a TTY, require a flag off one — --force/--yes — so scripts state intent explicitly.
  • Accessibility is the plain path. Screen readers read the stream linearly: spinners, redrawn progress bars, and heavy box-drawing are hostile to them. Your piped/mono output — plain lines, meaning in words — is also your accessible output; treat it as a first-class rendering target, not a degraded one.
  • Windows is a real terminal now. Windows Terminal + ConPTY speak ANSI and UTF-8; legacy conhost may need the virtual-terminal mode flag enabled (or just require Windows 10+). Remaining differences live at the edges: path separators, no real SIGINT semantics, CRLF in files (output \n — terminals translate).
  • Performance = batching. Terminal rendering is fast; syscalls per write aren't. Build each frame or report in a buffer, write once, flush. A flurry of tiny unflushed writes is both slow and flickery.
Carry this

Design the piped/plain rendering first — it's the accessibility story, the script story, and the CI story in one. The colorful interactive layer is progressive enhancement on top.

11

Testing & determinism

Terminal output looks hard to test — it's stateful bytes aimed at a pseudo-device — but becomes trivially testable with one architectural rule you've now seen three times: observe the world at the edge, pass it in as data.

  • Renderers are pure functions: (props, capabilities) → text, where capabilities carry width, color depth, unicode support, TTY-ness. No env reads, no clock, no isatty() deep in render code — those happened once at startup.
  • Snapshot ("golden") tests are the workhorse: render a component, compare against a checked-in expected frame. Failures show a visual diff; intentional changes re-record. This only works if renders are deterministic — inject timestamps, sort anything unordered, seed randomness.
  • Test the capability matrix, not one happy path: the same component at mono/16/256/truecolor, at 40/80/120 columns, unicode and ASCII. The corners are where alignment and meaning break — exactly the bugs chapters 06–08 describe.
  • Assert at the right layer: strip ANSI when testing content and layout; keep sequences when styling is the contract. For interactive flows, drive the state machine directly (event in → frame out) and save real-PTY end-to-end tests (expect, tmux-driven) for a smoke-test few.
Carry this

"Hard to test" almost always means "impure." Quarantine I/O, environment, and time at the program's edge, and the other 95% — layout, styling, degradation — becomes plain functions with golden-file coverage.

The ten commandments

  1. stdout is data; stderr is commentary; exit codes are the verdict.
  2. Check isatty() per stream; honor NO_COLOR, FORCE_COLOR, --color.
  3. Detect capabilities once at the edge; pass them down as data.
  4. Author color as semantic roles that degrade to mono without losing meaning.
  5. Never encode meaning in color alone — pair with a symbol or word.
  6. Measure text in cells, truncate in graphemes, strip ANSI before either.
  7. Design for 80 columns; enhance for more; re-measure on SIGWINCH.
  8. Every terminal state you flip — raw mode, alt screen, hidden cursor, SGR — is restored on every exit path, crash included.
  9. The plain rendering is the accessible, scriptable, CI-safe one: design it first.
  10. Keep renderers pure — (data, capabilities) → text — and golden-test the capability matrix.
